# F02–F05 — builtin invocation and process isolation

This is the current foundation for issue #40, not a claim of shell or utility parity. Builtins remain independent of the shell runtime; composition lives in `internal/builtinexec`.

## Invocation

`builtins.Context` carries `Args`, `CmdName`, `Dir`, streams, `Env`, `Ctx`, terminal dimensions and per-stream TTY flags, and an optional `Exec` callback. Callers supply the terminal metadata; it is not inferred by `Run`. `CancellationContext()` returns `Ctx`, or `context.Background()` when absent.

A nil `Env` inherits the process environment; a non-nil empty slice means an empty environment. Use `Environ`, `LookupEnv` and `Getenv` for invocation-local access. `Environ` returns a snapshot. Registered builtin environment reads use these accessors rather than modifying or reading the process environment directly (apart from the inherited fallback).

`builtins.Run(ctx, name, inv)` accepts a nil invocation and copies the context and its argument and environment slices. A nil `ctx` uses the invocation's cancellation context. It makes `Dir` absolute, substitutes empty input and discard output for nil streams, and sets `CmdName` to `name` only when blank. Unknown builtins return 127. Stream objects themselves are shared, not copied.

`Executor` is `func(context.Context, string, *Context) int`, a neutral nested-execution capability. `builtinexec.Run` composes exact builtin lookup with external execution using invocation-local cwd, environment, streams and PATH; it is not a complete shell launcher. `builtinexec.For` selects the default callback. The multicall entry point bridges interruption to invocation cancellation for non-interactive commands, with a forced-exit fallback described below.

`ExitStatus` maps cancellation to 130 and deadline exceeded to 124, and supplies success, failure, usage, internal, cannot-execute and not-found constants (0, 1, 2, 125, 126, 127). Process signal statuses use the 128 base where supported. Individual wrappers retain their own status semantics, including timeout's 124 and launch failures 125/126/127.

## F03 — invocation-local environment

`env` computes a non-nil child environment, including an empty slice for `-i`, and passes it through `Context.Env`. It never clears, sets, or restores process environment variables. `builtinexec.For("env")` now supplies the normal executor, so nested builtins and external children receive the same computed environment and directory. The compatibility paths also pass that environment without mutation. `env` retains its legacy preference for an executable regular file in its working directory before nested dispatch; resolution policy and cwd poisoning remain for F06. The shared executor otherwise retains builtin-first lookup.

The audit migrates backup controls (`cp`, `mv`, `ln`), `echo`/`printenv`, PATH lookup, terminal dimensions/colors, locale selection, HOME/login names, temporary directories, and time handling. `install` has no backup-environment implementation to migrate; adding utility flags remains U14. `sshc` carries environment into its SSH options (HOME, USER, SSH_AUTH_SOCK), `vi` passes it to shell child processes, and `devices` resolves storage/configuration paths from invocation HOME/XDG variables. Public web server/admin and editor APIs still inherit process state by default.

`Context.Location()` resolves invocation TZ without changing `time.Local` or caching global state. Unset TZ uses `time.Local`; empty or invalid TZ uses UTC. Zoneinfo names (including names such as EST5EDT when installed), a leading `:`, and absolute zoneinfo files are supported. It does not parse arbitrary POSIX TZ rule strings. `date` retains its existing timestamp-aware POSIX TZ parser for compatibility; extending that behavior consistently to the other utilities is future work. `ls`, `stat`, `touch`, `cal`, and diff headers use the shared location helper.

Concurrent invocation tests exercise conflicting PATH, TZ, backup suffixes and custom variables, including nested `env`, and assert the process environment remains unchanged. An AST guard prevents new direct process-environment access in builtin sources and vi/mweb entrypoints, with narrowly named exemptions for inherited fallback and process-level web APIs.

## F05 — cooperative cancellation and stream termination

`Terminal.StartFuncContext` gives an in-process callback a session context. `Interrupt` cancels it before closing the PTY and retains status 130. `Close` also cancels it. The UI passes that context through `builtins.Run`; legacy `StartFunc` remains available, but an arbitrary legacy callback cannot be forcibly stopped by Go. This does not change process sessions, suspend/resume, or shell job control.

Standalone non-interactive commands cancel on the first SIGINT/SIGTERM. Cooperative cancellation returns 130 (a context deadline returns 124). A second signal or a 500ms grace timeout forces process exit with `128 + signal` (130 for SIGINT, 143 for SIGTERM), so an unconverted operation cannot swallow interruption indefinitely. Terminal/signal owners (`vi`, the top/htop/btop aliases, `tm`, games, `sshc`, and `devices`) retain their existing handling. `timeout` also retains its existing handling pending F06. The bridge never subscribes to job-control signals.

`ContextReader`, `ContextWriter`, `CopyContext`, and `ReadFileContext` check cancellation between chunks (at most 32 KiB per stream operation). Converted commands use an invocation-local stream lifecycle; they do not modify the caller's context or close caller-owned streams. Reads/writes waiting on arbitrary Go streams return immediately on cancellation using a worker with its own buffer. There is at most one pending worker per sequential adapter operation, no idle workers between operations, and no background command/CPU loop is abandoned by these adapters. A worker blocked inside an uninterruptible caller-owned `Read` or `Write` remains until the owner closes/unblocks that stream; callers must arrange this before reusing/discarding it. Command-owned files are closed on return. This is a bounded strategy, not a guarantee that arbitrary Go I/O can be forcibly interrupted.

Migrated paths include `yes`, both `seq` number paths, repeated `shuf`, `printf`, `tail -f/-F` polling, formatted/unformatted `cat`, `tee`, recursive `cp` and cross-device `mv`; `sleep` already cooperated. The read audit covers head/wc/cut, checksums and hashes, base encodings/xxd, and the remaining text-stream commands (comparison, sorting input/output, split, translation, formatting and uuencoding). `install` has no copy implementation to migrate; `dd` and `watch` are not yet registered. `top-commands` is finite history analytics, not a refresh loop; the full-screen top tools are separate terminal owners.

The first stdout failure (including EPIPE/closed pipe) stops migrated indefinite output loops; `yes`, `cat`, `tee`, and `seq` return 1 rather than simulating SIGPIPE. Existing command-specific error statuses otherwise remain in place. This fixes previously ignored copy/write errors, not utility-option parity. Whole-input readers still buffer their input: cancellation-aware reads do not imply bounded-memory streaming.

## F04 — child-only process effects

`internal/proceffect` owns process-effect isolation without importing the registry. Its minimal capability is `Run(context.Context, Request, Invocation) int`: `Request` carries a priority adjustment and argv; `Invocation` carries the directory, exact environment and streams. `nice` snapshots `Context.Environ()` before crossing this boundary, preserving nil/inherited versus deliberately empty invocation environments. Arbitrary `Context.Exec` closures cannot cross a process boundary; `nice` now always uses the isolated child's default dispatcher, even with a nil executor. No parent thread is reniced.

The private `--misa-process-effect` multicall entry is not registered or listed. It adjusts the child, then re-execs into the dispatch stage. On Linux priority belongs to a thread: the adjusting thread is locked until exec, so the fresh target runtime's threads inherit the adjusted value. Both builtin targets (`builtins.Run`) and external targets execute after that adjustment. A denied adjustment prints the existing warning and still runs the target. `nice` without a command reads niceness only; Linux's raw `getpriority` result is normalized to the actual nice value rather than printing `20 - nice`.

Each parent-side launch owns a child process group; nested effect launches inside that isolated runtime share the owned group. Cancellation kills the group, waits for the direct child, and returns 130 (124 for a deadline). Ordinary target statuses are preserved, including `128 + signal`; malformed requests/helper startup failures use 125, cannot-execute uses 126, and not-found uses 127. This is not shell job control: foreground terminal ownership, stop/continue and pipelines remain worker/launcher work. A target which deliberately escapes the group is not contained by this capability. Inside an effect child, an inner-only context cancellation kills its direct child rather than the shared group (which would also kill its owner); remaining nested descendants are cleaned up when the outer owner is cancelled. F06 must unify this supervision with job/pipeline ownership.

Child dispatch uses exact bare builtin names first. An explicit path is external, relative to the invocation directory when not absolute. The former cwd-local executable and basename-builtin fallbacks are removed: an unrelated executable in cwd no longer silently overrides a builtin or PATH search. External lookup uses the invocation PATH, with F02 semantics (unset means not found; an explicitly empty PATH segment means cwd). Whether unset PATH should instead use an execvp-style default, and cwd poisoning when PATH is explicitly empty, are explicit F06 resolver-policy questions; this does not claim launcher unification or ENOEXEC shell fallback.

`Umask() (int, error)` is uncached. Linux/Android read `/proc/self/status`; if procfs is unavailable, and on other Unix systems, a re-executed child queries its inherited mask using set/restore **only in that child**. No mutex or temporary parent mutation is involved. Reader failures are reported rather than guessing a creation policy. `mkdir`, symbolic `chmod` and `mkfifo` share this reader; `cp` relies on kernel creation modes and has no separate umask reader. Future mask/credential/resource mutations must extend the child capability, not call process-global setters in registered builtin code. No `umask` or `ulimit` builtin is added here.

The audit covers builtin, vi, mweb and procmon sources. An AST guard rejects process priority/mask/resource/credential/root/session/group/cwd mutations and `signal.Ignore`, including aliased imports and function references. The sole narrow exception is htop's existing explicit selected-PID renice action: it may intentionally target Misa itself and is not an automatic wrapper side effect. `timeout` configures a **child's** `SysProcAttr.Setpgid`, not the host's group. Standalone CLI signal setup and the job leader are process owners outside registered builtin implementations.

Known multicall hosts explicitly opt in with `proceffect.EnableSelfHelper()` before dispatch and route the hidden flag to `builtinexec.ProcessEffect` before ordinary argument/test handling; the builtins package's own TestMain supplies the equivalent dispatch without an import cycle. With no registered helper, command execution reports `nice: process isolation unavailable in this host` and returns 125; fallback umask queries return an error, never re-executing an unknown host. Linux/Android procfs reads still work without a helper. Android CLI hosts support this protocol, but the c-shared APK runs inside Android's `app_process`, not a multicall Misa executable: S21 owns APK helper wiring. Non-file streams cross pipes and are non-TTYs; real file descriptors retain terminal behavior. Output copiers are joined before return, including after cancellation, so they cannot keep writing a caller buffer after `Run` returns. A caller-owned `Write` already in progress must be unblocked by its owner; cancellation still kills the child promptly, but cannot forcibly interrupt arbitrary Go writer code. An input worker blocked in a caller-owned `Read` can remain until its owner unblocks it, using its own copy buffer as in F05. The implementation is pure Go, adds no dependencies, builds on Android with CGO=0, and provides unsupported stubs outside Unix (the broader builtin package does not yet build on Windows).

Measured on this Linux host, the dedicated package's `BenchmarkRun` costs approximately **2.5–2.9 ms/invocation** (including adjustment and dispatch re-execs, excluding target work); it is a measurement, not a portability/performance guarantee. Procfs umask reads do not pay that startup cost; fallback reads do.

## Boundaries and follow-up

- **F06/S15:** Adopt the child-effect request in the shared launcher and persistent shell worker. Shell creation-mask state, mutation, redirections and resource/credential operations are not implemented by F04; S15 owns `umask`/`ulimit`.
- **F05 limitations:** Opening a named FIFO or other blocking filesystem metadata/open operations may block before a cancellable stream exists. Recursive diff checks cancellation on each comparison, but not while iterating a directory itself; finite CPU-bound sort/diff/fmt work and a single large formatting operation are not comprehensively interruptible. Do not classify these commands as universally safe in-process solely because their stream paths cooperate. Future worker/capability isolation (S05) remains necessary.
- **F06:** `timeout` retains legacy dispatch and signal/group handling, including `-s`, `-k`, `-p`, `-f` and ENOEXEC concerns. An integer-returning executor cannot preserve those signal semantics; no injected-timeout guarantee is provided. The `sort` external compressor path was inspected and is also left for F06. Unify launcher resolution, signal supervision and cleanup there.

- **Vi follow-up:** The registered `vi` builtin passes the invocation environment to its shell commands, but the terminal still uses process streams. Shell working directories depend on the edited filename (or process cwd), not consistently on the invocation directory. Cancellation is not propagated. These need a separate design without changing the UI frontend inadvertently.
